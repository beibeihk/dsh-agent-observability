# Observable failure taxonomy

Every finding carries a stable type, severity, Session ID, event seq evidence, explanatory message and relevant metric/threshold. Findings describe **observed patterns**, not inferred private reasoning, causality, or task correctness. `failure_id` identifies a finding in a snapshot; the session's event sequences are the evidence anchors.

| Rule | Definition and evidence | Default threshold | Example | False-positive risk / not-a-failure |
|---|---|---|---|---|
| F01 Missing result | `tool/call` has no non-replacement terminal `tool/result`; requires a closed turn or caller-finalized interval and complete capture | Any unmatched call | seq 4 call, completed turn at seq 8, no matching result | Running calls are pending. Cancelled/fork-closed turns are exempt. Gaps or bounds suppress absence-based conclusions. An explicitly finalized open fixture is an analyst declaration, not inferred liveness. |
| F02 Duplicate terminal | More than one terminal result for the same turn/step/call identity | More than 1 | call seq 4, results seq 5 and 6 | `surfaceOp: replace` is not another terminal result. Call IDs reused across different steps remain distinct. |
| F03 Repeated equivalent call | Consecutive calls have same tool and canonical JSON argument HMAC, within one turn and window | 3 calls within 60,000 ms of run start | lookup `{x:1,y:2}` repeated with reordered object keys | Polling/idempotent validation can intentionally repeat. Informational argument differences such as timestamps prevent a match. Arrays preserve order; malformed JSON compares literally. The key is ephemeral and cannot link sessions. |
| F04 Tool error loop | Same tool produces error results in consecutive call steps; a success, different tool or step gap resets the run | 3 | lookup fails in steps 1, 2, 3 | Intentional retries can be valid; warning, not session failure. Multiple failures within a single parallel step do not satisfy consecutive-step definition. |
| F05 Excessive attempts | Durable `assistant/message` plus `assistant/attempt` settlements in one step exceed limit | More than 3 | three discarded attempts and one accepted message | Retry success remains completed. Lost pre-settlement attempts are unobservable. A single terminal failed attempt is not a retry. |
| F07 Abnormal termination | `turn/end.reason.kind` is error/interrupted; blocked/max-tokens produce warning | Any | error closer at seq 9 | `aborted` is cancellation, `forked` is synthetic fork closure, completed is normal. A tool error followed by recovery does not imply this finding. No finding is fabricated from missing live status. |
| F08 Long tool | Paired result timestamp minus call timestamp exceeds limit | More than 30,000 ms | call at 1000, result at 32001 | This includes approval/policy/scheduling; a legitimately slow tool can trigger warning. Negative clock deltas clamp to zero and are not a duration claim. Pending tool age is not inferred. |
| F09 High failure ratio | errors / (successes + errors) exceeds configured ratio after minimum denominator | More than 0.5 with at least 4 settled calls | 3 errors out of 4 | Cancels/pending calls excluded. Small denominators suppressed. Intentional probes can fail frequently without failing the task. |
| F10 Request churn | Logged changed headers plus context changes after first context exceed threshold | At least 5 | multiple provider/model/tool/context changes | Deliberate routing, compaction or configuration changes can be appropriate; severity info. Header events do not equal model requests. |
| T01 Tool error | A non-cancellation tool result has error status | Each error result | structured `LookupError / NOT_FOUND` | Severity info explicitly distinguishes a local error from a failed session. Recovery still completes. |

F06 Turn Without Progress is **not implemented**. The public event log does not supply a universal task-state oracle; a tool success or additional text is insufficient proof of useful progress. Context utilization and hidden request/context estimates are also absent. Future domain adapters may add a task-specific state metric with explicit evidence.

F01 is suppressed on partial capture. Positive findings on captured evidence may still appear when truncated; every exporter includes `integrity` so consumers can filter incomplete cases. An empty failure list means “no enabled pattern detected in this captured interval,” not “the agent is correct.”

The synthetic evaluation counts Session/type pairs, rather than every repeated finding instance. This prevents long error loops from inflating precision through many T01 records. Threshold edge cases and legitimate cancellation/replacement/parallel/recovery behavior also have direct tests.
